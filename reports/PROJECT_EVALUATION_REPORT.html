1. Executive Summary & Problem Formulation

Autonomous software development and automated patch repair models frequently suffer from a critical correctness failure: they cannot reliably judge the security or functional soundness of their own output. When evaluated against typical software benchmarks, LLM agents actively engage in specification gaming or reward hacking—passing narrow happy-path assertions by silencing exceptions, truncating inputs, or returning hardcoded dummy responses, while leaving the underlying security vulnerability fully exploitable.

The Autonomous Code Validator (ACV) solves this problem by replacing probabilistic model confidence with a deterministic, multi-oracle executable verification engine. A patch is only approved if it simultaneously neutralizes the security exploit, passes the native unit test suite, introduces zero new AST violations, and preserves protected testing infrastructure.

2. Multi-Oracle Architecture & Linux Kernel Containment

ACV enforces code correctness and host safety through an unbypassable four-stage verification pipeline:

  • Static AST Security Oracle (acv-rules): High-speed Abstract Syntax Tree visitor inspecting patch diffs for unsafe patterns (e.g., subprocess.Popen(shell=True), unsafe YAML loaders, ReDoS regexes) in <65 ms.
  • Dynamic Exploit Invalidation Oracle: Applies the candidate patch to a clean repository clone and executes the targeted Proof-of-Concept (PoC) exploit script. The patch is verified only if the exploit is completely neutralized (exit code 1 or controlled exception).
  • Behavioral Regression Oracle: Runs the repository's native pytest test suite. Guarantees zero functional regression (exit code 0).
  • Protected Test Shield: Detects and blocks any candidate patch that attempts to alter test assertions or disable security checks.
  • Linux OS Kernel Containment: Subprocess execution is strictly bounded via resource.setrlimit() capping RAM at 768 MB, CPU time at 30–60s, and output files at 16 MB. Worker processes execute inside independent process sessions (os.setsid) terminated via os.killpg(SIGKILL) upon timeout, preventing zombie workers or runner freezes.

3. High-Performance Compute: C-DAC Infrastructure & Quantized Open Models

To eliminate reliance on commercial APIs (such as OpenAI/Anthropic), prevent data leakage, and ensure reproducible local execution, the team leveraged high-performance computing allocations provided through C-DAC (Centre for Development of Advanced Computing) Cloud / HPC Infrastructure.

C-DAC Workstation Node: 1× NVIDIA GPU Node with 48 GB VRAM (A40 / RTX 6000 Ada tier).
Allocation Constraint: Time-budgeted batch compute allocation windows required maximizing inference throughput per GPU hour while running completely offline without external API rate limits or latency penalties.

Running full unquantized 70B parameter models exceeded VRAM or throughput constraints. To achieve optimal performance within our 48 GB budget, we implemented local quantized open-source model execution via vLLM and Ollama:

  • DeepSeek-R1 / DeepSeek-Coder-33B (AWQ 4-bit / BF16): Quantized to fit within ~22 GB VRAM, allowing concurrent execution of the model and the sandbox runner. DeepSeek synthesized adversarial assertions and patch repair candidates at high token velocity (~45 tokens/sec).
  • Moonshot Kimi-k3 / K1.5: Deployed for multi-file repository context analysis and long-context diff tracking, ensuring patches did not break cross-file dependencies.
  • Qwen2.5-Coder-32B (4-bit AWQ): Allocated ~18 GB VRAM for rapid syntactic repair generation.
  • Inference Efficiency: 4-bit quantization delivered a 3.2× throughput speedup with <0.8% degradation in patch verification quality, enabling complete offline batch evaluation during our scheduled C-DAC compute window.

4. Day-by-Day Practical Engineering Milestones

The project progressed through six distinct engineering phases from initial AST mutation prototypes to production verification:

Timeline Phase Objective Engineering Implementation Roadblock & Practical Resolution
Day 1 AST Mutation Core Line-constrained AST mutation visitor (ast.NodeVisitor). Comparison, boolean, and return mutations bound strictly to patch diff hunks. Issue: Global AST corrupted helper files.
Fix: Bound visitor to git diff boundaries.
Day 2 Sandbox & Kernel Isolation Dynamic runner with Linux resource.setrlimit() bounding RAM to 768 MB and CPU to 30–60s. Process grouping with os.setsid(). Issue: Malicious loops froze test runner.
Fix: Process-group watchdog with SIGKILL.
Day 3 Deterministic Dual Gate Multi-oracle engine: PoC exploit must fail (exit 1) AND regression suite must pass (exit 0). Enforced protected test shields. Issue: Flaky oracles rejecting gold fixes.
Fix: Enforced 100% gold-patch soundness gate.
Day 4 C-DAC Setup & Checker Benchmark Configured C-DAC 48GB VRAM node. Built acv qualify CLI benchmarking acv-rules against Bandit across 11 vulnerability tasks. Result: Achieved 90.3% F1 score (vs 64.2% Bandit) running in 62 ms (vs 10,279 ms).
Day 5 Multi-Task Benchmark & Negative Control Live git clone & dynamic execution across curated CVE benchmark tasks and 20 scenarios. Added Pallets Click as negative control. Issue: ReDoS in sqlparse recursion.
Fix: 3-way structured PoC classifier.
Day 6 Hardening CLI & Web Console Engineered acv repo-harden to synthesize isolated branches (acv/harden-<task>) and PR markdown. Launched real-time web dashboard. Result: Fully automated vulnerability remediation, verification, and branch delivery.

6. Checker Qualification Benchmark: acv-rules vs Bandit

We benchmarked our AST engine against the standard Python security linter bandit across 11 vulnerability tasks representing 10 CWE families:

Analyzer TP FP FN TN Precision Recall F1 Score Latency
acv-rules (Our Engine) 28 1 5 21 96.6% 84.8% 90.3% 62 ms
bandit (Baseline SAST) 17 3 16 19 85.0% 51.5% 64.2% 10,279 ms

acv-rules achieved a +26.1% higher F1 score than Bandit while running 165 times faster (62 ms vs 10,279 ms). Bandit exhibited a 48.5% false-negative rate on subtle injection variants (missing 16 vulnerable samples).

7. Automated Hardening CLI & Verification Deliverables

All audits, benchmarks, and pull request syntheses execute directly from the terminal via the unified acv CLI:

$ uv run acv qualify

# 2. Run the 44-candidate two-sided dynamic execution audit:
$ uv run acv audit

# 3. Execute benchmark suite across 20 live scenarios:
$ uv run python scripts/benchmark_repos.py
