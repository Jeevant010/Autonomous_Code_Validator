1. Executive Summary & Problem Statement

Autonomous code generation agents (such as SWE-agent, OpenHands, and LLM coding assistants) suffer from a fundamental failure mode: they cannot reliably judge the security or functional correctness of their own generated output. When tested against typical coding benchmarks, AI agents frequently engage in specification gaming or reward hacking—returning hardcoded dummy responses, disabling test assertions, or applying surface-level syntactic tweaks that pass narrow unit tests while leaving severe security vulnerabilities wide open.

The Autonomous Code Validator (ACV) solves this problem by replacing model confidence with an executable, multi-oracle verification pipeline. Candidate code is executed inside an isolated Linux kernel sandbox and evaluated across four mandatory gates: (1) Static AST Security Rules, (2) Exploit Invalidation (dynamic Proof-of-Concept execution), (3) Behavioral Regression Suite (native pytest assertions), and (4) Protected Testing Infrastructure Shields. Across 7 real-world production open-source repositories and 20 live scenarios, ACV achieved 100% verdict accuracy with zero false accepts and zero false rejects.

2. Day-by-Day Practical Development & Engineering Log

The project was developed in iterative phases, transitioning from theoretical AST mutation to live multi-repository kernel containment and automated Git PR branch synthesis:

Day / Phase Core Objective Practical Implementation & Engineering Actions Observed Challenges & Technical Solutions
Day 1 AST Mutation & Attack Loop Constructed line-constrained AST mutation engine (ast.NodeVisitor). Implemented comparison inversion (>= to >), boolean flips, and return mutations limited strictly to lines touched by patches. Issue: Whole-file syntax bleed corrupted unmodified helper functions.
Fix: Bound mutator to unified git diff hunk boundaries.
Day 2 Sandbox & OS Containment Built dynamic subprocess sandbox runner. Embedded Linux kernel resource.setrlimit() capping RAM at 768 MB, CPU at 30–60s, and file write limits at 16 MB. Issue: Infinite loops in mutated code froze test runner and spawned zombie workers.
Fix: os.setsid() session grouping with os.killpg(SIGKILL).
Day 3 Dual-Execution Gate Implemented the two-sided multi-oracle gate: Exploit Proof-of-Concept must fail (exit 1) AND regression suite must pass (exit 0). Enforced protected test file shield. Issue: Flaky oracles rejecting valid human fixes.
Fix: Ground-truth dual verification: gold patch must pass 100% before verifier qualifies.
Day 4 Checker Qualification Developed acv qualify CLI. Benchmarked acv-rules against Bandit across 11 security vulnerability tasks representing 10 distinct CWE families. Result: acv-rules achieved 90.3% F1 score (vs 64.2% Bandit) and ran in 62 ms (vs 10,279 ms).

6. Negative Control: Proving Zero False Alarms on Clean Code

A critical failure mode of automated security gates is "alarm fatigue"—rejecting healthy code. To validate specificity, we introduced Pallets Click (version 8.1.7) as a negative control:

  • Clean Baseline Evaluation: ACV cloned Click, executed the security audit probe, ran all 56 functional unit tests, and inspected AST rules. Verdict: ACCEPT (0 vulnerabilities, 100% tests pass).
  • Injected Backdoor Mutant: When an adversarial subshell injection (subprocess.Popen(..., shell=True)) was injected, ACV's AST checker immediately detected the rule violation and flipped the verdict to REJECT.

7. System Architecture & Containment Guarantees

ACV enforces containment through an unbypassable four-stage pipeline:

  • Static Rule Oracle (acv-rules): Lightweight AST inspection detects known unsafe calls (subprocess.Popen(..., shell=True), yaml.load(Loader=Loader), unsafe regexes) in <65 ms.
  • Security Exploit Oracle: Executes the specific vulnerability Proof-of-Concept. The exploit must be completely neutralized (exit code 1 or safe exception).
  • Behavioral Regression Oracle: Runs the repository's native pytest test suite. Guarantees the patch does not break existing application behavior (exit code 0).
  • Linux Process Isolation: Uses resource.setrlimit() to strictly bound CPU and RAM, isolating worker processes in independent process sessions (os.setsid) to prevent fork bombs and hanging loops.

9. Oral Defense & Viva Cheat-Sheet (Answering Reviewer Questions)

Q1: "Did you just build an AI wrapper or prompt ChatGPT?" Answer: No. The LLM is strictly an untrusted candidate generator at the edge. The core contribution is the deterministic verification engine. The model's self-assessed confidence has zero authority; code must execute inside an OS sandbox against real exploits and unit test suites.
Q2: "Why not just use Semgrep, Bandit, or SonarQube?" Answer: Static analyzers only read syntax without execution. In our qualification benchmarks, Bandit missed 48.5% of real vulnerability variants (F1 of 64.2% vs our 90.3%) and flagged false alarms on safe sanitizers. Dynamic execution of real exploit scripts combined with pytest suites is required for ground-truth correctness.
Q3: "Did you just hardcode these examples?" Answer: No. Every evaluation executes live git clone operations into ephemeral Linux directories, builds isolated .acv-deps/, and runs pytest. Any new repository can be integrated simply by declaring task.json with an external Proof of Concept.
Q4: "Does your gate reject everything? What happens on clean code?" Answer: We explicitly evaluated Pallets Click (CWE-None) as a negative control. On clean code, ACV passed all 56 tests and verified zero vulnerabilities, producing an immediate ACCEPT. When a backdoor mutant was injected, it flipped to REJECT, proving zero false alarms.
Q5: "How do you prevent an AI from 'fixing' a bug by deleting code or returning null?" Answer: That is enforced by our Behavioral Oracle. A patch must pass both the security exploit (exit 1) AND the project's native unit test suite (exit 0). A patch that deletes functionality or returns early fails the pytest behavioral suite and is instantly rejected.
Q6: "How do you protect your host machine when executing untrusted AI code?" Answer: Containment is enforced at the operating system level using Linux kernel resource limits (resource.setrlimit) capping RAM at 768 MB, CPU time at 30–60s, output files at 16 MB, running inside independent process sessions, and killing runaway trees with os.killpg(SIGKILL).
Q7: "Can your system produce deliverables for software engineers?" Answer: Yes. The acv repo-harden command creates an isolated local Git branch (acv/harden-<task>) and generates a complete pull_request.md containing before-and-after attack logs, unit test pass verification, and modified file diffs ready for review.
