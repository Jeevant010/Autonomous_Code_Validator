The problem

One exploit is not a proof.

Most patch checks stop at "the exploit no longer works." This audit asks three questions at once and records where the answers disagree.

01

Exploit blocked

The original attack must fail against the candidate. A blocked exploit is necessary, not sufficient.

dynamic
02

Behavior preserved

The functional suite must still pass. A security fix that breaks the program is not a fix.

dynamic
03

Checker calibrated

The rule pack must stay quiet on safe code. The audit measures recall, precision, and false-repair rate.

The gate

Two signals, four outcomes.

Every candidate lands in exactly one cell. The report counts all four, including the cells that look successful but are not.

Two-sided verdict matrix

Security fails -- security theater -- obvious reject
Correct verdicts -- of -- candidates
Residual risk -- false pass -- false rejection

The report keeps both. A verifier that hides its misses is not a verifier.

The pack

Ten workers, ten failure modes.

Each task has a vulnerable worker, a gold fix, a safe variant, two plausible bad variants, an exploit, and a functional suite.

The second opinion

The checker is not the oracle.

Built-in rules and Bandit are scored on the same tasks. The gate uses both as signals, not as truth.

Read the bars carefully. Recall is measured on the vulnerable worker plus the bad variants. Precision is measured on the gold fixes plus the safe variants. A high-recall checker can still reject safe code.

What the gate missed

The residual cases are part of the result.

These are the two candidates where the gate and the ground truth disagree. The audit names them, explains them, and keeps them in the denominator.

Reproduce

One command. Real subprocesses.

The audit runs offline. It copies each candidate into an isolated temporary directory, runs the exploit and functional suite, invokes both checkers, and writes the report.
